WEATHERPARSE INSTALLATION GUIDE
===============================

This guide walks through a manual install of WeatherParse on a freshly installed Debian based server, including a
Raspberry Pi running Raspberry Pi OS Lite.

WeatherParse is based on Acuparse by Maxwell Power (AGPL-3.0). The old Acuparse automated installer and its
"acuparse" command line tool are not part of WeatherParse; follow the manual steps below.

Note:
    Supported: Debian 12 (bookworm) with PHP 8.2, and Debian 13 (trixie) with PHP 8.4, including Raspberry Pi OS
    Lite based on them.

Raspberry Pi
============

If you are connecting an Access directly to the Pi's Ethernet port, also read the Raspberry Pi Direct Connect guide
(https://github.com/mobilevoid/weatherparse/blob/main/docs/other/RPI_DIRECT_CONNECT.txt) and the section
"Direct Connection (Raspberry Pi)" below.

Raspberry Pi tips
-----------------

- Disable Wi-Fi power saving. On a Pi 4 the Wi-Fi can silently stop passing traffic with power saving on.
  With NetworkManager (the default on Raspberry Pi OS based on Debian 12 and 13) create
  /etc/NetworkManager/conf.d/wifi-powersave-off.conf containing:

      [connection]
      wifi.powersave = 2

  Then restart NetworkManager or reboot. Check with: iw dev wlan0 get power_save

- Raspberry Pi OS based on Debian 13 keeps the systemd journal in RAM only, so it is lost on power loss or reboot.
  Use /var/log/syslog (rsyslog) for history.

- Optional: a small watchdog (a systemd timer that pings your router every minute, reconnects Wi-Fi after a few failed
  minutes and reboots after a longer outage, at most once an hour) keeps a remote Pi reachable without a trip to it.

Manual Installation
===================

- Switch to the root account:

      sudo -i

- Set your timezone. On Debian 13 the old names such as US/Central moved to the tzdata-legacy package; use the
  current names such as America/Chicago:

      timedatectl set-timezone America/Chicago

- Install the required packages (PHP 8.2 on Debian 12 or PHP 8.4 on Debian 13; the php meta packages pick the right
  one):

      apt update
      apt install -y apache2 mariadb-server php libapache2-mod-php php-mysql php-curl php-gd php-cli \
          ffmpeg imagemagick git

  For a direct connect Raspberry Pi also install:

      apt install -y dnsmasq iptables-persistent

  Optional, for troubleshooting the Access traffic:

      apt install -y tcpdump

- Secure MariaDB:

      mariadb-secure-installation

Get WeatherParse
----------------

    git clone https://github.com/mobilevoid/weatherparse.git /opt/weatherparse
    chown -R www-data:www-data /opt/weatherparse/src/usr /opt/weatherparse/src/pub/img

Setup Database
--------------

Create the database and user. Use a strong password of your own:

    mariadb -e "CREATE DATABASE IF NOT EXISTS weatherparse;
    CREATE USER 'weatherparse'@'localhost' IDENTIFIED BY 'STRONGPASSWORD';
    GRANT ALL ON weatherparse.* TO 'weatherparse'@'localhost';
    GRANT EVENT ON weatherparse.* TO 'weatherparse'@'localhost';
    GRANT RELOAD ON *.* TO 'weatherparse'@'localhost';
    GRANT SUPER ON *.* TO 'weatherparse'@'localhost';
    FLUSH PRIVILEGES;"

Apache
------

    cp /opt/weatherparse/config/weatherparse.conf /etc/apache2/sites-available/
    cp /opt/weatherparse/config/weatherparse-ssl.conf /etc/apache2/sites-available/
    a2enmod rewrite ssl
    a2dissite 000-default
    a2ensite weatherparse weatherparse-ssl
    systemctl restart apache2

SSL Certificate
---------------

By default Apache uses the snake oil certificate for HTTPS. That is fine for the Access, which does not check the
certificate. If you also serve the site under a hostname, install a real certificate for it.

Access TLS (OpenSSL 3)
----------------------

The Access uses an old TLS version. On OpenSSL 3 (Debian 12 and 13) allow it in /etc/ssl/openssl.cnf, in the
[system_default_sect] section:

    MinProtocol = TLSv1.1
    CipherString = DEFAULT@SECLEVEL=1

Restart Apache after changing it.

Web Installer
-------------

Visit http://<your server IP>/ to run the web installer. It creates the database schema and the first admin account.

Cron
----

Edit root's crontab (crontab -e) and add:

    * * * * * /usr/bin/php /opt/weatherparse/cron/cron.php > /opt/weatherparse/logs/cron.log 2>&1

If you use a camera (see "Webcam Installation" below) also add:

    */10 * * * * /bin/bash /opt/weatherparse/cam/webcam > /opt/weatherparse/logs/cron.log 2>&1
    15 3 * * * /bin/bash /opt/weatherparse/cam/webcam cleanup > /opt/weatherparse/logs/cam-cleanup.log 2>&1

Initial Configuration
=====================

- After the web installer, add your Access/smartHUB MAC address and sensor IDs.
    - Visit /admin/settings and open the Sensor tab.
    - Enter your MAC address with no spaces, dashes, or colons.
    - Enter your 8 digit Iris (5-in-1) or Atlas (7-in-1) ID including any leading 0's.

Check Installation
==================

Initial Readings
----------------

It can take some time for your initial readings to populate the dashboard. You will see a "No Data Received!" message
until the first readings are processed and stored. Current Access firmware reports every 5 minutes.

See section "Initial Readings" in the Troubleshooting Guide
(https://github.com/mobilevoid/weatherparse/blob/main/docs/TROUBLESHOOTING.txt).

Syslog
------

WeatherParse logs to syslog as weatherparse(<version>). Watch the data flowing through your system and look for any
trouble. Enable debug logging for a more detailed view.

    tail -f /var/log/syslog | grep weatherparse
    journalctl -t weatherparse -f

Getting Access Data to WeatherParse
===================================

The Access sends its readings to atlasapi.myacurite.com. WeatherParse receives them when that name points at your
WeatherParse server. There are two ways.

Note:
    Access users can also change the Access upload server with the tool at /admin/access once logged in, instead of or
    as well as redirecting DNS.

DNS Override on Your Network
----------------------------

Set up a local DNS override for atlasapi.myacurite.com pointing to the IP address of your WeatherParse server.
See the DNS Redirect Guide (https://github.com/mobilevoid/weatherparse/blob/main/docs/other/DNS.txt).

Direct Connection (Raspberry Pi)
--------------------------------

Plug the Access into the Pi's Ethernet port. The Pi runs dnsmasq on that port, hands the Access an address and
answers its DNS. Debian 12 and later name the onboard Ethernet port end0 (older systems: eth0); use the name your
system shows (ip -br link).

- Give the Ethernet port a fixed address, for example 192.168.6.1/24 (in NetworkManager: a manual IPv4 address with
  never-default set, so it is not used for internet).

- Two resolvers. dnsmasq answers only the Access, on the Ethernet port, and points the AcuRite upload host at the
  Pi's address on that port. The Pi itself keeps using your router's DNS over Wi-Fi, so it still sees AcuRite's real
  address (needed to forward readings to MyAcuRite). Do not put atlasapi.myacurite.com in /etc/hosts.
  /etc/dnsmasq.conf (also in config/dnsmasq-hub.conf.example):

      # Serve only the Access port; the Pi itself keeps using your normal DNS
      interface=end0
      except-interface=lo
      bind-interfaces
      no-dhcp-interface=wlan0
      dhcp-range=end0,192.168.6.50,192.168.6.100,255.255.255.0,24h
      # The Access gets the redirect; everything else goes to public DNS
      no-hosts
      no-resolv
      server=8.8.8.8
      server=1.1.1.1
      address=/atlasapi.myacurite.com/192.168.6.1

  Stop dnsmasq from becoming the Pi's own resolver: add DNSMASQ_EXCEPT="lo" to /etc/default/dnsmasq, then
  systemctl restart dnsmasq and resolvconf -u. Check: getent hosts atlasapi.myacurite.com on the Pi shows AcuRite's
  public addresses, and dig +short @192.168.6.1 atlasapi.myacurite.com shows 192.168.6.1.

- Current Access firmware ignores the DNS server handed out by DHCP and asks 8.8.4.4 directly. Redirect the Access
  subnet's DNS to the Pi's dnsmasq, share the Pi's internet with the Access, and save the rules:

      iptables -t nat -A PREROUTING -i end0 -s 192.168.6.0/24 -p udp --dport 53 -j DNAT --to-destination 192.168.6.1:53
      iptables -t nat -A PREROUTING -i end0 -s 192.168.6.0/24 -p tcp --dport 53 -j DNAT --to-destination 192.168.6.1:53
      iptables -t nat -A POSTROUTING -o wlan0 -j MASQUERADE
      echo net.ipv4.ip_forward=1 > /etc/sysctl.d/90-weatherparse.conf && sysctl --system
      netfilter-persistent save

- After adding the rules the Access may keep using its old DNS connection. Power cycle the Access, or clear its
  connections with: conntrack -D -s <access ip>

Manually Update Access Server
-----------------------------

Change to WeatherParse:

    curl -d 'ser=<WEATHERPARSE FQDN>' http://<ACCESS IP>/config.cgi

Reset to default:

    curl -d 'ser=atlasapi.myacurite.com' http://<ACCESS IP>/config.cgi

smartHUB
--------

AcuRite's smartHUB service (hubapi.myacurite.com) no longer exists. A smartHUB still works with WeatherParse (point
hubapi.myacurite.com at your server with a local DNS override), but its readings cannot be forwarded to MyAcuRite.

Troubleshooting
---------------

If your Access readings are not arriving, see section "Hardcoded DNS Servers" in the Troubleshooting Guide
(https://github.com/mobilevoid/weatherparse/blob/main/docs/TROUBLESHOOTING.txt).

Database Trimming
=================

Readings get stored in multiple temporary database tables. This temporary data should be cleaned up regularly to avoid
ballooning the database.

When the external updater runs, it archives the most recent readings to the archive table for later use.

Database trimming is done by the MariaDB event scheduler.

- Enabling trimming is recommended, unless you need the additional data.
    - When enabled, tower data is also trimmed. Should you wish to keep tower data, use that option instead.

If the event scheduler is not behaving, make sure MariaDB is up to date and its tables were upgraded after a version
upgrade:

    mariadb-upgrade

Barometer Readings
==================

You can modify the barometer readings used by WeatherParse. Set your Access/smartHUB to use station pressure using
MyAcuRite and adjust your offset.

Readings are only modified in WeatherParse and sent to 3rd party sites. It does not modify the reading MyAcuRite
receives from your Access/smartHUB.

Check the syslog and watch for your changes. Once your Access/smartHUB is reporting updated readings, set the
offset in the WeatherParse settings.

Uploading Data
==============

Detailed instructions for each provider are in docs/external.

- The cron job set up earlier processes your weather data and sends updates to external sites automatically, as
  required.
    - Data is only sent to external sites when there is new data to send and enough time has passed for CWOP updates.

Info:
    It's recommended to disable the updating of Weather Underground from your Access/smartHUB/MyAcuRite when using
    WeatherParse.

Master Sensor
-------------

By default, WeatherParse uses the Iris/Atlas sensor to upload data to external sites. To upload data from a tower,
change the Master Temp/Humidity Sensor.

Changing the sensor sends those readings externally instead of the Iris/Atlas data. You can also choose to use the tower
readings for the data archive or use the readings from the Iris/Atlas.

Realtime Updates
----------------

WeatherParse supports an RTL dongle together with the RTL Relay service (a separate project from Acuparse,
acuparse/rtl-relay) for realtime updates to weather data. See the Realtime Guide
(https://github.com/mobilevoid/weatherparse/blob/main/docs/REALTIME.txt).

MyAcuRite Responses
===================

Access
------

Note:
    The Access sends data using TLS 1.1 encryption. A certificate is required to receive data from the Access (the
    default snake oil certificate works).

WeatherParse forwards each Access reading to atlasapi.myacurite.com and returns MyAcuRite's answer to the Access.
It looks the address up through DNS directly (not /etc/hosts), and never forwards to an address that belongs to
the WeatherParse server itself, so the redirect that brings the readings in cannot cause a loop. If MyAcuRite cannot
be reached, or forwarding is disabled, WeatherParse answers the Access itself.

When MyAcuRite receives your readings, it responds with JSON in the following format:

    {
      "sensor1": "",
      "PASSWORD1": "",
      "timezone": "",
      "elevation": "",
      "ID1": ""
    }

    Variable    Description
    timezone    Local timezone offset of the Access.
    ID1         Weather Underground Station ID.
    PASSWORD1   Weather Underground Station Password.
    sensor1     Sensor used to send data to Weather Underground.
    elevation   Elevation of the Access in feet.

- A typical response:

      {"timezone":"00:00"}

smartHUB
--------

Warning:
    The smartHUB is obsolete and no longer supported by AcuRite. The AcuRite Access is the recommended replacement.

AcuRite no longer accepts updates from the smartHUB. The smartHUB will continue to work with WeatherParse, but will not
send updates to AcuRite. WeatherParse always responds to the smartHUB with:

    {
      "localtime": "00:00:00",
      "checkversion": "224"
    }

With localtime set to the local time of your WeatherParse install.

Email and Mailgun Settings
==========================

WeatherParse will attempt to use a locally installed email server. You can enable Mailgun instead in your Admin
Settings.

Mailgun
-------

You will need your Mailgun API key and domain to configure. See Mailgun's current instructions for adding a domain.

Email Outage Notifications
==========================

Outage notifications are sent to all registered admins. You can configure some simple values for outage checking; the
system will email you when no data is received.

The updater first checks to see if there is new data to send. If there isn't, it will start the email process. If
there is no new data due to updates not being received in the configured period, WeatherParse will send an email at
your chosen interval.

Email Battery Notifications
===========================

WeatherParse emails when a device reports a low battery: the AcuRite Access hub (its backup batteries), the Atlas,
the Iris, or a tower sensor. Configure it in Admin, Settings, Features, Battery Alerts:

- Enabled: on by default once email works (a local mail program or Mailgun). Low batteries are always logged.
- Recipients: email addresses separated by commas. Leave empty to email all admins, like outage notifications.
- Reminder Every: hours between reminders while a battery stays low (default 24). 0 sends no reminders.
- Battery OK Email: email once when the battery reports normal again (default yes).

The cron job checks every run. A device that has not reported for an hour is skipped, since that is an outage and not
a battery problem. One email lists every low device, when it was first seen low, which batteries to replace, and links
to the dashboard and the Sensor Status page. The state is kept in the battery_alert database table.

Tower Sensors
=============

WeatherParse allows the addition of as many Tower sensors as the Access/smartHUB will pass along. You can choose which
sensors are shown publicly or only to logged-in users. Towers are configured and arranged using the admin settings.

- WeatherParse also supports Indoor/Outdoor Temp and Humidity monitors, as well as lightning towers.

Lightning Sensors
=================

You can have a main Lightning sensor on your Atlas, as well as one Tower sensor. Configure the Lightning sensor settings
in your admin site settings in order to display those readings.

Filter Access Readings
======================

The Access can send unwanted erroneous readings. Filtering is enabled by default. You can disable the filtering of these
readings in Admin, System Settings, Sensor tab.

WeatherParse checks the incoming Access readings and drops any that meet ALL the conditions below. Dropped readings
do not flow through to MyAcuRite and are not saved to the database.

The dropped readings are reported in your logs and WeatherParse still sends a response to your Access.

Filtered Readings
-----------------

Readings that have a tempF of -40 OR 0, relH of 0 OR 1, and 0 wind speeds. As well as 0 light and UV readings from
the Atlas.

Additional Outputs
==================

The primary user interface uses AJAX to pull the most recent HTML formatted data from the API automatically.

WeatherParse includes a display mode for better viewing while in full-screen.

- Display Mode: http(s)://<yourip/domain>/display
    - Force light theme: http(s)://<yourip/domain>/display?light
    - Force dark theme: http(s)://<yourip/domain>/display?dark

Additionally, you can request Bootstrap 5 formatted HTML, JSON array(s), or plain text formatted for watermarking.

- See the API Guide (https://github.com/mobilevoid/weatherparse/blob/main/docs/API.txt).

Webcam Installation (optional)
==============================

The webcam script in the cam directory captures and processes images from an IP camera. You need to be able to get a
snapshot from your camera over http, or an RTSP stream. ImageMagick and ffmpeg must be installed.

Images are stored in src/pub/img/cam (website) and cam/archive (local archive).

The webcam script operates in three modes, set with MODE in cam/config.env:

    Mode       Description
    combined   The camera and WeatherParse are on the same network. Use this in almost all installs.
    local      Runs on a host local to the camera (such as an NVR) and sends the image to a remote WeatherParse
               server. The website image is NOT updated on this host.
    remote     Processes an image sent by a "local" host, on the WeatherParse server.

Warning:
    Use combined when the camera and WeatherParse are reachable from the same machine. Setting local on the
    WeatherParse server itself means the website camera image never updates.

Combined System Setup
---------------------

- Copy config.env from cam/templates to the cam folder and edit it: MODE='combined', the camera URL (an http
  snapshot URL, or with USE_RTSP=1 an rtsp:// URL such as rtsp://<user>:<password>@<camera ip>/<stream path>),
  and your watermark text.

      cp /opt/weatherparse/cam/templates/config.env /opt/weatherparse/cam/

- Image retention: KEEP_DAYS in cam/config.env (default 30, 0 keeps everything). The daily cleanup job removes
  website day folders and archive images older than that, so the archive cannot fill your SD card.

- Cron (root): capture every 10 minutes, cleanup once a day:

      */10 * * * * /bin/bash /opt/weatherparse/cam/webcam > /opt/weatherparse/logs/cron.log 2>&1
      15 3 * * * /bin/bash /opt/weatherparse/cam/webcam cleanup > /opt/weatherparse/logs/cam-cleanup.log 2>&1

  The script uses a lock, so a slow run is skipped instead of overlapping the next one.

Local/Remote Setup
------------------

Local System

Note:
    Local scripts need to be updated by hand if the webcam script changes.

- On the system local to your camera, copy the cam folder from a WeatherParse checkout
  (https://github.com/mobilevoid/weatherparse) to /opt/weatherparse/cam.
- Copy config.env from cam/templates to the cam folder and edit it, setting the mode to local.
- Set up a cron job to process the image:

      */10 * * * * /bin/bash /opt/weatherparse/cam/webcam > /dev/null 2>&1

- Set up SSH keys, so you can log in to your remote host from the local host without a password:

      ssh-copy-id -i ~/.ssh/{YOUR_KEY} {USERNAME}@{HOSTNAME}

Remote WeatherParse System

- Copy config.env from cam/templates to the cam folder and edit it, setting the mode to remote.

      cp /opt/weatherparse/cam/templates/config.env /opt/weatherparse/cam/

Backup/Restore
==============

A backup script is included in cron. Local installs need to enable it manually.

- See the Backup Guide (https://github.com/mobilevoid/weatherparse/blob/main/docs/other/BACKUPS.txt).

Southern Hemisphere Support
===========================

Users in the Southern Hemisphere generally install their stations pointing North and not South for the solar panels
to operate properly. This leads to an incorrect (opposite) wind direction reading. WeatherParse can switch your wind
direction readings to support installations in the Southern Hemisphere.

The raw wind degrees received by WeatherParse are reversed and used for all external uploaders and system readings.
Raw data forwarded to MyAcuRite is not modified.

- Available under Southern Hemisphere Support on the System Settings, Sensor tab.

Google Settings
===============

WeatherParse has no analytics or tracking code. The only Google setting is reCAPTCHA, which is off by default.

Invisible reCAPTCHA
-------------------

reCAPTCHA loads on the authentication and contact forms, and when requesting a password reset.

- Sign up for a reCAPTCHA account (https://www.google.com/recaptcha).
- Select Invisible reCAPTCHA when registering your new site.
- Enter your site key and secret in your site settings.

Debug Server
============

You can send MyAcuRite readings to an external debug server. To enable, manually edit src/usr/config.php.

- Find debug->server->show and change it to true.

The debug tab will now appear in your system settings.
