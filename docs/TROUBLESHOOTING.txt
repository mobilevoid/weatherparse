WEATHERPARSE TROUBLESHOOTING GUIDE
==================================

This guide helps with common issues installing and using WeatherParse. It is not a complete guide. If you need help,
open an issue on GitHub (https://github.com/mobilevoid/weatherparse/issues).

Initial Readings
================

When you first install WeatherParse, you may see a "No Data Received!" message on your dashboard. WeatherParse needs
to receive and process its first readings from your sensors before the dashboard can be rendered. Current Access
firmware reports every 5 minutes.

After your initial readings are received, cron processes them into archive readings. If you see a "No Archive Data!"
message, there may be a problem archiving your readings. Some dashboard features require archive data. It is critical
that cron runs the archive job. Look for the message (SYSTEM){CRON}: Archive Updated in your syslog (see "Syslog"
below). Until the archive job has completed successfully, the dashboard shows an error and no data.

If your dashboard does not update after 5 to 10 minutes, check your syslog to make sure data is flowing. Also check
that your DNS is redirected, OR that you set the upload server on the Access directly. See the DNS Redirect Guide
(https://github.com/mobilevoid/weatherparse/blob/main/docs/other/DNS.txt).

Logs
====

Syslog
------

The best way to troubleshoot your installation is the syslog. WeatherParse logs there as weatherparse(<version>).

    tail -f /var/log/syslog | grep weatherparse
    journalctl -t weatherparse -f

Note:
    Raspberry Pi OS based on Debian 13 keeps the systemd journal in RAM only. After a reboot or power loss, use
    /var/log/syslog for history.

Apache Access Log
-----------------

The Apache access log contains everything Apache received, including the readings from your Access/Hub. It shows
whether WeatherParse is receiving data from your devices.

    tail -f /var/log/apache2/access.log

Apache Error Log
----------------

The Apache error log contains the errors and warnings generated by Apache and PHP.

    tail -f /var/log/apache2/error.log

Cron Log
--------

    tail -f /opt/weatherparse/logs/cron.log

Sensor IDs and MAC Addresses
============================

Without a MAC configured for your Hub or Access, WeatherParse has no way of knowing what data to listen for. Set a MAC
and an Iris (5-in-1) or Atlas (7-in-1) sensor ID in the admin settings to begin receiving and uploading your readings.

Sensor IDs and MAC addresses are printed on the devices themselves. If you can't find them, the syslog reports all
sensors and MAC addresses it does not recognize:

    grep weatherparse /var/log/syslog | grep '\[ERROR\]'

For sensor IDs the log format is (ACCESS/HUB){ATLAS/IRIS/TOWER}[ERROR]:

Cron Job
========

The cron job is essential. It runs the archiving, update checking, and external uploads. If your station stays
offline or nothing is sent to external providers, check it first.

    crontab -l | { cat; echo "* * * * * /usr/bin/php /opt/weatherparse/cron/cron.php > /opt/weatherparse/logs/cron.log 2>&1"; } | crontab -

Make sure the line appears only once in root's crontab; a duplicate line makes every upload run twice.

Raspberry Pi
============

See the Raspberry Pi Direct Connect guide
(https://github.com/mobilevoid/weatherparse/blob/main/docs/other/RPI_DIRECT_CONNECT.txt) and the Install Guide
(https://github.com/mobilevoid/weatherparse/blob/main/docs/INSTALL.txt), section "Direct Connection (Raspberry Pi)".

WeatherParse forwards readings to MyAcuRite by looking up atlasapi.myacurite.com through DNS directly, not through
/etc/hosts, and never forwards to the WeatherParse server itself. The local redirect on the Pi therefore cannot cause
a never ending cycle of readings, and no "secondary" upload server is needed.

Wi-Fi Drops on a Raspberry Pi 4
-------------------------------

If the Pi's Wi-Fi silently stops passing traffic while the Pi keeps running, turn off Wi-Fi power saving (see the
Install Guide, section "Raspberry Pi tips") and check with: iw dev wlan0 get power_save

Hardcoded DNS Servers
=====================

Current Access firmware ignores the DNS server handed out by DHCP and asks 8.8.4.4 directly. A DNS override on your
own DNS server is then never consulted, and the Access sends its readings straight to AcuRite.

- If the Access is behind a Linux box you control (the Raspberry Pi direct connect setup), redirect the Access
  subnet's DNS traffic to your own DNS server with iptables NAT rules. See the Install Guide, section
  "Direct Connection (Raspberry Pi)".
- Otherwise, set the upload server on the Access itself with the tool at /admin/access.

To see what the Access is doing, capture its traffic on the server (replace end0 with your port name):

    tcpdump -nn -i end0 host <access ip>

After changing DNS rules the Access may keep using its old DNS connection. Power cycle the Access, or clear its
connections with: conntrack -D -s <access ip>

Installation Errors
===================

If you experience unexpected results while completing the web install, remove your config file and retry:

    sudo rm /opt/weatherparse/src/usr/config.php

In more extreme cases, you may also need to drop and recreate the WeatherParse database (see the Install Guide,
section "Setup Database").

Access Device
=============

If you're not receiving data from your Access, make sure you have a DNS resolvable hostname set for the upload server
and/or a DNS redirect in place. Then reboot your Access. The Access can at times need several reboots before it sends
data.

The Access talks to WeatherParse using TLS 1.1. On OpenSSL 3 (Debian 12 and 13) this must be allowed in
/etc/ssl/openssl.cnf; see the Install Guide, section "Access TLS (OpenSSL 3)". When using Let's Encrypt, certbot can
overwrite the Apache config and remove TLS 1.1 support; check /etc/apache2/sites-available/weatherparse-ssl.conf and
make sure any Include of /etc/letsencrypt/options-ssl-apache.conf is commented out. The default configuration is in
the config folder of your WeatherParse directory.

MyAcuRite Offline
-----------------

If MyAcuRite is offline, WeatherParse responds to your Access and stores your readings, but they are not backfilled to
MyAcuRite after the outage. The Access can store data and send it later, but with WeatherParse it believes MyAcuRite
was online and the readings stored.

You will see a warning in your syslog when this happens.

Extended Outages
----------------

When your Access stops sending data for an extended period, your WeatherParse data becomes stale. This creates errors
in your dashboard and API. Once your Access is back online, some calculations need enough new data before they work
again. This can take up to 24 hours.

NTP
===

The date and time are critical, both on the server and on your Access.

The Access checks pool.ntp.org for the time. Make sure your Access can reach it, or redirect pool.ntp.org to a local
NTP server.

On the server, systemd-timesyncd (or another NTP client) must be running. Check with: timedatectl

Cisco Switches
==============

If your Access constantly reboots or reconnects when connected to a Cisco switch, enable Portfast.

    config terminal
    interface FastEthernet0/XX
    spanning-tree portfast
    end

Hub Device
==========

MyAcuRite Support
-----------------

AcuRite has ended support for the smartHUB and its service (hubapi.myacurite.com) no longer exists. WeatherParse
receives and stores smartHUB readings and responds to your hub. Readings are not uploaded to MyAcuRite and are only
stored locally. You can still use the hub to upload to external providers.

Inaccurate Readings
===================

WeatherParse filters Access readings for erroneous values by default. See the Install Guide, section
"Filter Access Readings".

If the station's own readings look wrong (for example temperature far above nearby official stations in sun), check
the sensor: a blocked or stopped aspiration fan, a dirty radiation shield, or a failing temperature/humidity element
are common causes. Compare with a nearby official station before blaming the software.

If you have old erroneous readings in your archive table, you can clean them with SQL. Modify the queries below to fit
your needs, and back up first. Use your own database name.

Main:

    mariadb weatherparse -e "DELETE FROM archive WHERE tempF='-40' AND (relH='0' OR relH='1')"

Towers:

    mariadb weatherparse -e "DELETE FROM tower_data WHERE sensor='<SENSOR_ID>' AND tempF='-40' AND (relH='0' OR relH='1')"

Database Tables After a Power Loss
----------------------------------

An unclean shutdown can mark tables as crashed. Check and repair them:

    mariadb-check --auto-repair --check weatherparse

Git Repository
==============

If you change the source code locally, git pull fails unless you commit or stash your changes. To discard local
changes and return to the release state run git reset --hard (this removes your local code changes; your config files
are not tracked by git and are kept).
